# 工程可靠性与知识库维护

本次范围是单轮 RAG 的可靠运行、索引任务与页面反馈，不含会话记忆。

## 1. 已实现的数据流

```text
CLI 导入完整资料 → prepared generation
页面点击本地重建 → 保存 pending 任务并锁定准备资料 ID
→ 后台 running，记录 preparing/encoding/vector_write/validating/publishing
→ 新 generation 校验通过 → SQLite 事务切换 active 指针
→ 任务 succeeded，页面轮询展示“已发布”
```

页面的重建只使用 **CLI 已经准备好的资料快照**，不会重新扫描原目录。
新增、替换、移除文件后，先重新执行 `ingest`；缺少 prepared 快照时不会创建构建任务。
提交后若准备资料又被替换，任务以 `prepared_input_changed` 失败，重新提交使用最新资料。

管理 API：

- `POST /api/v1/index-jobs`：请求只接受 `kb_id`，返回持久化任务和 HTTP 202。
- `GET /api/v1/index-jobs?kb_id=...`：最近 20 个任务。
- `GET /api/v1/index-jobs/{job_id}`：状态、阶段、generation、错误码及可操作说明。
- `POST /api/v1/index-jobs/{job_id}/retry`：仅失败/中断任务允许重试；产生新任务并保留旧记录。

页面管理入口只执行本地编码；配置为 Viking 时会拒绝并提示走显式允许费用的 CLI。
页面本地检索、证据预览不会因切换到远程索引而自动产生编码费用；远程按钮和费用选择单独展示。
生成、收费增强、显式远程检索以及维护写操作都检查本机客户端、Host 和浏览器 Origin。

## 2. 失败和重启

原有 generation 发布模型保持：新代独立构建，成功校验后才事务切换 active；普通异常标失败，不切换旧指针。

任务状态保存在新增的 `index_jobs` 表中，不依赖内存。
启动时扫描 `pending/running` 和残留 `building`，只有能够同时取得该库的作业锁和构建锁时才认定执行已中断；其他进程持锁时保留原状态。
中断任务不会自动重跑，页面显示原因并允许用户重新构建。

发布与任务成功确认有一个很短的事务间隔。若此时退出，重启会核对任务对应的 generation：
当该代已为 ready 且 active 指向它时，补记为 succeeded，而非错误地判为 interrupted。
普通执行异常也执行同样的核对，避免发布成功却显示失败。

后台工作线程为 daemon；服务关闭不无限等待模型或数据库操作。
任务执行中真正退出后，下一次启动按持久化记录和文件锁恢复。
它不是断点续算：失败或中断后重建新代，已发布旧代继续保留。

## 3. 启动和停止

在迁移后的 `C:\Users\15853\DEBUG_RAG` 中：

```powershell
.\scripts\start-local.ps1
.\scripts\stop-local.ps1
```

启动脚本从 Settings 获取实际 runtime 路径。它通过 `/health/live` 的 `project_root` 检查端口上的服务来源，不能把旧目录服务当作新目录服务复用。
其他服务占用 8001 时明确报错，不停止对方。
后台启动使用隐藏窗口，记录进程 ID、启动时间、项目目录和日志位置。
停止脚本同时核对项目目录、解释器、命令行和进程启动时间，拒绝 PID 复用或其他项目记录。
它仅停止本项目 API，不删除 Docker 数据卷。

Milvus 的命名卷独立于项目目录。迁移后 Compose 保留相同 project name 和 volume name，复用 `debug-rag-p0_milvus-data`；配置文件的挂载路径随新目录更新。
